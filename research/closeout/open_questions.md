# Open questions — 仅存档，不启动

这些是可提问的方向，不是已确认的 research gaps、新颖算法或立项建议。当前没有足够证据支持以它们重启 RCHAM。

| 问题 | 为什么值得记下 | 目前不能声称什么 |
|---|---|---|
| First-time unexpected query | q1 后的动作不能回溯改善第一次检索；需要单独衡量可访问证据与首次读取代价 | 不能说首次 recall 没人做过，或层级搜索已优于平面搜索 |
| Lifecycle benchmark 的测量语义 | 应区分“保留某个 ID”“保留任一等价证据集合”“模型答对”和“任务状态有效” | 当前手工 ID oracle 不是真实 answer accuracy，也未证实已有 benchmark 都不足 |
| Real I/O cost accounting | 节省比较次数可能不节省端到端时间；冷读取、重算、utility probing 有成本 | 本项目没有测 GPU/CPU/SSD 代价，不能从计数推导性能优势 |
| Nonstationary future reuse | 话题切换与新状态可改变未来需要的信息，过去贡献只是一种可能信号 | 没有证据据此推荐新的 reuse predictor；现有研究需要另行核实 |

## 两个只记录的可证伪问题

1. **评测标准敏感性：**在未来的新项目中，同一缓存轨迹若分别按指定 evidence ID 和任一充分证据集合评分，方法排序是否会改变？当前 cross_event 的标签冲突为这个问题提供动机，但本轮不替换标签、不重评分为真实 QA、不运行实验。这首先是测量问题，未建立论文新颖性。
2. **语义版本一致性：**针对有明确版本与生效时间的任务，保留过时但高访问的事实是否会比缺失事实造成更多答错？需要真正观察到的公开 failure 和强基线才能立项。它可以属于水利知识库等独立任务，不是本项目追加状态图、decay 或 controller 的理由。

架构层面的唯一保留原则是：**将精确数据的可恢复性、当前任务贡献与未来存储分配视为不同契约。**这是一条避免错误设计的约束，不是新的 Attention 结构或已验证优化方案。

未来只有用户明确发起新项目，并且存在新的理论动机或经核实的公开 failure evidence，才另行设计方法与实验。不得通过改名或沿用 Phase 编号自动重启。
